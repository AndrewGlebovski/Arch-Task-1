# Преподавательская оценка студентов

*Предисловие.* Вообще C++ мне нравится больше, но проще и быстрее было сделать на python. Он поддерживает интерфейсы (если класс наследуется от typing.Protocol) и read-only классы (если аннотировать `frozen=True`). Настоящей инкапсуляции нет, но по соглашению, приватные методы и поля начинаются с `_`. На мой взгляд, он подходит для демонстрации решения.

## Overview

В `domain/values.py` объявлены конкретные классы для большинства значений, чтоб не использовать примитивные типы. Для всех ID используется UUID. По отдельным файлам раскиданы соответствующие сущности:

- `Student` - личная информация про студента.
- `Evaluation` - оценка студента в рамках какого-то критерия.
- `Criterion` - задает критерий оценки и диапазон оценки.
- `Rubric` - набор критериев.

Студенты, рубрики и оценки хранятся в собственных репозиториях. Все классы ссылаются друг на друга через ID, а не через указатели. `TotalScore` - итоговая оценка студента, которая является отдельным классом от `Score`, так как имеет другую область значений. `TotalScoreCalculator` соответственно позволяет посчитать `TotalScore`, используя выбранную стратегию. `AppFacade` - запоминает интерфейсы репозиториев, калькулятора и экспортера и позволяет добавлять и просматривать студентов, рубрики, критерии и оценки, а также экспортировать результаты. `container.py` - инициализирует фасад требуемыми реализациями. `ui/console.py` - связывает консольный интерфейс с методами фасада.

## DDD Map

### Ubiquitous language

`Student`, `Criterion`, `Evaluation`, `Rubric` - все объекты называются так же, как их назвал заказчик.

### Entity & Value Object

Entity - идентичность важнее значений (`Student`, `Criterion`, `Evaluation`). Value Object - идентичности нет, просто значения (`Score`, `MaxScore`, `Weight`, `StudentId`, `TotalScore`).

*Комментарий.* Объективного критерия, чтоб разделять эти понятия не нашел, поэтому взял довольно абстрактный.

### Invariants

Проверка `0 <= score <= max` происходит при создании в `EvaluationFactory.create`. Та же проверка при изменении оценки в `Evaluation.change`.

Проверка `критерий только из рубрикатора` происходит в `EvaluationFactory`. Та же проверка при изменении оценки в `Evaluation.change`. При подсчете в `TotalScoreCalculator`.

### Repository

Интерфейсы для репозиториев лежат в `domain/repos.py`. In-Memory реализации, которые хранят все в `dict`, находятся в `infra/memory_repos.py`.

### Domain Service

Тут только калькулятор итога, так как он не подходит под определение `Entity` и `Value Object`.

## SOLID

- `Single Responsibility Principle` - разделение на `domain`, `app`, `infra` and `UI` (разделение на уровне модулей, а не на уровне классов).
- `Open/Closed Principle` - в калькуляторе используется паттерн стратегия, поэтому при появлении нового способа оценивать задачи код править не нужно.
- `Interface Segregation Principle` - три разных интерфейса репозитория, а не один на всех.
- `Dependency Inversion Principle` - `EvaluationFactory` и `AppFacade` зависят от интерфейсов, а не от реализаций.

## Design Patterns

- `EvaluationFactory` (Factory, порождающий)
- `AppFacade` (Facade, структурный)
- `WeightedSumStrategy` (Strategy, поведенческий)
